## 🚩 Flagship finding: redirect-destination resolution is implemented three times, and the copies disagree

This is the single most corroborated defect in the sweep — three independent finder agents converged on it from different angles (duplication, and two separate correctness-risk passes), and it's the one most likely to ship visibly wrong output to a client.

**The problem.** `resolveRedirectDestinations()` (`src/renderer.js:18232`, runs on every save) is the canonical resolver: it recursively chases Consolidate chains with cycle detection, propagates the `'404'` sentinel, and excludes Fragment rows. Two other places reimplement the same logic from scratch instead of calling it or reading its output:

- **The Redirect Editor's inline display** (`renderer.js:21850-21911`) does a one-hop lookup instead of recursing the chain, and its 404-handling falls back to the master's live URL instead of propagating the sentinel.
- **`exportRedirectMap()`** (`renderer.js:22259-22326`, reachable from Migration → Export Redirect Map (CSV)… and the unified Export dialog's "Redirect Map (CSV)" option) has only two branches (`kill` and `computedPath`) with no consolidate handling, no 404-sentinel handling, and no Fragment guard.

**Concrete divergences, all confirmed:**
1. A Consolidate chain A→B→C shows B's URL in the Redirect Editor but the file saves C's URL — a reviewer approves one thing and the file ships another.
2. A Consolidate row has its nav assignment cleared by design (`applyConsolidateTarget`), so it has no Computed Path and falls through both of `exportRedirectMap`'s branches — **every consolidation 301 is silently missing from the CSV handed to the client's dev/ops team.** On a migration where consolidation is a large share of the work, this is a materially incomplete deliverable.
3. A page explicitly marked for intentional deindex (`Redirect_Destination === '404'`) is exported as `Destination URL: 404, Status Code: 301` — a literal broken redirect rule.
4. After an SME resolve pass, a page whose `Final_KKE` is Kill but whose `KKE_Recommendation` is still Keep gets no redirect row at all (`exportRedirectMap` reads `kkeCol()`, not `finalKkeCol()`).

`buildRedirectsSheet()` (the Migration Tracker's Redirects sheet, `renderer.js:19247`) already does this correctly by calling `resolveRedirectDestinations()` first — it's the existing proof that the fix works.

**Fix.** Export the resolver's inner logic (`resolveFinalUrl`, its `rowByUrl` Map, and the `isFragmentRow` guard) as one shared function and have both the Redirect Editor's display and `exportRedirectMap()` call it instead of re-deriving. One resolver means the editor, the saved file, and the CSV can never disagree again.

## Performance

All of these are scale-dependent — described at the app's own stated design target of ~4,000 rows / ~500 sitemap nodes, where "fine at 500" routinely becomes "visibly stalls at 4k."

- **`project-store.js:160`** — `saveAll()` does `DELETE FROM rows` + full re-insert on **every** save, even a single-cell edit. Modeled at 4,000×70 columns: ~18MB of JSON re-stringified per save, 85-120ms in the transaction, on the tightest autosave debounce in the app (400ms for `.transmission` projects). The `rows` table already has a stable `idx` primary key — an `INSERT OR REPLACE` on just the changed indices would make autosave cost O(changed rows) instead of O(all rows).
- **`renderer.js:3042`** (`renderVisibleRows`) — Tears down and recreates every visible sidebar row (~40-50 rows × ~10 child elements + a click listener each) on every scroll frame **and** on every row selection — so arrow-key/j-k navigation rebuilds the entire visible window per keystroke just to move one `.selected` class.
- **`renderer.js:5383`** — `refreshRowInList()` ignores the row index it's given and does the same full rebuild, fired with no debounce on every keystroke in the field-bar meta inputs — each rebuilt row also re-runs a loop-invariant header lookup that could be hoisted once.
- **`renderer.js:578`** — The sidebar search input has no debounce: every keystroke runs a full `Object.values(row).some(...)` scan across every row × every column (~400k allocations on a 4k×100-col crawl) **and** a synchronous main-process `fs.readFileSync`+`writeFileSync` of `prefs.json`. The 150ms debounce pattern already exists elsewhere in the same file (`setupGlobalSearch`) and isn't reused here.
- **`renderer.js:14006`** — Every keystroke in a nav slug input triggers a full cascade: tree recalc, a per-row `state.navNodes.find()` join over every placed row, a per-row breadcrumb walk that re-climbs the tree at each level, and a consolidate-display sweep — all with no `id→node` index anywhere in the file (`state.navNodes.find` appears 54 times).
- **`renderer.js:16172`** — `suggestBulkNavTarget()` calls `suggestNavFromUrl()` (which does a `new URL()` per row per path level) once per selected target with no memoization — filtering to 1,000 unplaced pages before a bulk sitemap-assign produces on the order of 10s of millions of URL constructions synchronously before the dialog paints.
- **`renderer.js:9781`** — `applyConsolidationGroup()` calls `clearNavAssignment()` per row in a consolidation group, and that function ends with a full `renderNavEditor()` (complete tree DOM rebuild) whenever the nav editor is open — which it always is here, since the dialog is only reachable from the Sitemap toolbar. A 20-page group triggers 19 complete tree rebuilds back-to-back.
- **`renderer.js:11936`** — `renderMenusView()` is O(items² + items×navNodes): `childrenOf()` re-filters the whole item array per parent, and two separate linear `state.navNodes.find()` scans run per row. `seedMenuFromContentTree('All levels')` legitimately produces 500-800-item menus, so every drag-drop reorder or item add costs ~2.5M comparisons.
- **`renderer.js:21856`** — `renderRedirectEditor()` does an O(rows) `.find()` per Consolidate/Kill-with-target row plus an O(nodes) scan, inside a loop that already re-runs on every keystroke of an undebounced search box — O(rows²) on a crawl with hundreds of Kill/Consolidate rows. `resolveRedirectDestinations()` already builds the `rowByUrl` Map this needs; extract it into a shared helper. *(Corroborated independently by two finder agents, one of which also flagged the missing virtual scrolling on this view — already tracked in `TODO.md`'s "Virtual scrolling in redirect editor" item, but the O(n²) lookup cost is a distinct, additional defect beyond just adding virtualization.)*
- **`main.js:3059`** — The computed-column tokenizer/parser/evaluator is pure JS with zero Node dependencies, yet lives in the main process — every Recalculate structured-clones the entire crawl to main and back over IPC, and re-spreads the full row object once per definition inside the per-row loop.
