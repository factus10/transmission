Some spreadsheets arrive with KKE recommendations already generated outside the app — for example, `AI KKE` (from Screaming Frog's AI analysis). These are distinct from the app's own recommendation engines (the built-in Assess/Rubric feature, and the GA-driven `Suggested_KKE` system — see Done, below) and need to be surfaced so auditors can compare multiple recommendation sources.

GA KKE shipped as its own dedicated system (computed columns + config dialog), not via a generic column-detection mechanism — this item is now specifically about `AI KKE` and other truly external, unrecognized columns
- [ ] **Display external assessments in field bar** — show an external KKE column's value as a read-only badge (e.g. "AI: Keep") in the audit bar. The `Suggested_KKE` badge already does this for the app's own GA + Rubric sources; this item is about surfacing genuinely external columns like `AI KKE` the same way
- [ ] **Assessment comparison filter** — filter to rows where an external assessment column (e.g. `AI KKE`) disagrees with the app's own recommendation. GA-vs-Rubric disagreement within the app's own `Suggested_KKE` engine already has a dedicated filter (`_suggested-disagree` / `_suggested-mismatch`) — this item is about arbitrary externally-supplied columns, not GA
- [ ] **Bulk accept external assessment** — action to copy an external assessment column's values into `KKE_Recommendation` for all (or filtered) rows, as a starting point that the auditor then refines. ### Visual Sitemap / Menu Visualization
The shared box-tree engine (`src/sitemap-template.js`) backs both the nav sitemap and the per-menu sitemap, so all of these land in one place and benefit both surfaces.

- [ ] **Dynamic color legend** *(do this first — the item below depends on it, and it fixes a live bug)* — the legend today has **no color vocabulary at all**: `fillLegend()` (`src/sitemap-template.js:578`) emits three fixed card shapes (single page / stacked / root) plus one free-text note, and that note's default (`DEFAULT_LEGEND.colorBand`, `:71`) is the hardcoded sentence *"Color band = node depth (customizable)"*. Nothing in the legend reflects the color scheme actually in play. Build a legend that is **derived from the resolved scheme** — one entry per color currently in use, rules first, then per-node overrides. The hard part already exists: `condSummary()` (`:670`) already renders human-readable rule labels ("Depth = 2", "Tag: Academics", "Links to another site") for the Colors tab; the legend just never calls it
- [ ] **Ad-hoc per-node coloring with legend notes** *(depends on the dynamic legend above)* — per-node color overrides already exist (right-click context menu → `S.nodeOverrides`, which win over all rules), but there is nowhere for a manually-colored node to explain itself. Once the legend is dynamic, let the user attach a note/label to an ad-hoc color so it appears as its own legend entry. **Do not** build this as a standalone override-notes feature bolted onto today's static legend — there is no per-color legend to add an entry to
- [ ] **More color-rule condition types** — the rule engine supports `depth`, `depthRange`, `parentId`, `value`, `external`, `field`, and `always` (`resolveColor()` / `matchesRule()`, `src/sitemap-template.js:162-168`). Add further condition types so more of the audit's own signal can drive the diagram. **Needs candidates chosen before it's actionable** — nothing here defines "done" yet. Options the data model already supports without touching the engine (since `node.fields` is host-declared in `navSitemapFieldDefs()`): assigned page count (hub vs leaf vs heavy section), net-new/hub status, has-notes, phase-is-set, and the **KKE composition of a node's assigned rows** — the last being the one that would let the sitemap show the audit's actual verdict
- [ ] **"Left-aligned" layout mode** — a third layout option alongside the current threshold-driven horizontal/vertical stacking (`shouldBeVert()` / `subtreeBox()` / `layoutNode()`). Exact semantics TBD — explore before building
- [ ] **Excalidraw export** — a fourth destination alongside client HTML / PDF / PNG / Miro, and the one that fills the gap between the view-only HTML export and Miro: something a stakeholder can *rearrange and annotate* with no account, no seat, and nothing to provision. Also the escape hatch for trees the layout can't make readable (see the ~550-root case behind `computeSitemapShape()`) — today the only "a human moves these by hand" answer is Miro.
  - **Shape it exactly like `buildMiroSitemapPlan()` (`src/renderer.js:16800`)** — host-side layout via the pure `window.SitemapLayout` (`compute()` → positions, `resolveStyle()`, `visibleNodes()`, `connectorWidthFor()`), then emit. The tail is far shorter than Miro's: no OAuth, no auth Worker, no credit limiter, no partial-board failure mode. It ends at the existing `saveTextFile` IPC (`preload.js:39`), same as the client-HTML and menu-JSON exports.
  - **No new dependency.** `.excalidraw` is plain JSON — writing a scene does not require `@excalidraw/excalidraw`. Keep it that way; that's what makes this cheap in a signed/notarized universal build, and it matches the D3/mermaid removal precedent.
  - **Fidelity should beat the Miro export**, because most of the constraints documented in CLAUDE.md's Miro section don't exist here: arbitrary hex on both fill and stroke, real corner radius (vs Miro's binary `rectangle`/`round_rectangle`), numeric `strokeWidth` with no integer-slider snapping (so the 1.5px band stops rendering hair-thin), `solid|dashed|dotted` mapping 1:1 to the app's three line styles with nothing flattening, real `fontSize` with no undocumented minimum, and unclamped connector widths. Biggest win: arrows take explicit `points`, so the app's **shared-bus** connector geometry (stub down → span across siblings → drop into each child) can be reproduced literally instead of approximated with per-edge elbows that route through cards.
  - **Verify the element schema against a current build before writing it** — the format is versioned and thinly documented in places. Pin a version; don't trust recalled field names.
  - **One-way, like Miro.** No round-tripping client edits back in.
  - **Treemap follows nearly free** via the existing `exportBoxes()` emit contract (boxes are rectangles). **Sankey doesn't** — no ribbon primitive, so it hits the same approximation the Miro path does; skip it or accept connector-as-band there too.

### Medium Priority
- [ ] **Numeric comparison operators in field filters** — the sidebar field filter (`openFieldFilterPopup()` / `fieldFilterMatches()`) supports `is-blank`, `is-not-blank`, `contains`, `not-contains`, `equals`, `not-equals`, `starts-with`, `ends-with` — all string ops. Add numeric comparison so columns like word count, sessions, GA_Score, status code, and crawl depth can be filtered by magnitude.
  - **Match the convention that already exists — don't re-decide it.** The rubric field-rule engine (`main.js:2335-2338`) has done this all along: `gt` / `gte` / `lt` / `lte` via `parseFloat` on both sides. Because `NaN > x` and `NaN < x` are both false, non-numeric cells (blank, `"N/A"`, stray text) are already excluded from *both* directions. Reuse that semantic verbatim — if the sidebar filter picked, say, coerce-to-0 instead, the same column would filter differently in a rubric rule than in a sidebar filter on the same spreadsheet.
  - Add all **four** ops (`gte`/`lte` too, not just `gt`/`lt`) — near-free, and it matches the established vocabulary.
  - **While you're here:** the two subsystems use divergent operator naming for the same concepts — rubric snake_case (`is_not`, `starts_with`, `is_empty`) vs field-filter kebab-case (`not-contains`, `starts-with`, `is-blank`). Worth deciding deliberately whether to converge them rather than adding a third dialect
- [ ] **More edit options in the Redirect Editor** — the editor is read-mostly today: per-row you can type a destination, pick a nav node, or toggle the `404` sentinel (`renderRedirectRow()`, renderer.js), and the only bulk operation is Find/Replace over destination text plus **Re-derive from sitemap** (`resyncNavBasedRedirects()`). Missing:
  - **Multi-select** — a per-row checkbox + select-all-visible header checkbox, respecting the active status filter / search / Find-filter (so "select all" means "all *shown*"). Mirror the nav editor's `state.navMultiSelected` + `#nav-multi-bar` pattern (`setNavNodeSelected()` / `toggleNavSelectAllVisible()` / `updateNavMultiBar()`) rather than inventing a second selection model
  - **Clear destination — one row and in bulk** — `clearRedirectDestination(row, origIndex)` (renderer.js:2466) already exists for the Kill-cleanup flow; wire it to a per-row ✕ and to a bulk "Clear destinations" action. Note it must clear provenance too — `writeRedirectDestination()` is the single write path and an empty cell has no author
  - **Bulk set `404`** — the sentinel is a real decision ("let this URL die"), and today it's a per-row toggle only; deciding it for a whole filtered set (e.g. every `/tag/*` page) is the common case
  - **One undo per bulk action** — route every bulk write through `pushBulkEditUndo(items, label)`, as URL-variant and Non-200 triage do, so a thousand-row change reverses in one Cmd+Z
  - **Semantics to settle first — "delete a row" is not a delete.** The redirect list is *derived*, not a user-managed table: `renderRedirectEditor()` recomputes it every render from Kill/Consolidate rows plus pages whose `Computed Path` differs from their URL. Clearing a destination therefore leaves the row on screen with a blank destination; the row only leaves the list when the underlying page stops needing a redirect (KKE changes, nav assignment cleared, etc.). So decide what a row-level ✕ means — most likely **clear the destination** (with an explicit "this page still needs one" state), possibly alongside a separate action that changes the page's disposition. Do not build something that silently hides a row still owed a redirect: a missing rule is exactly the failure the Redirect Health Check exists to catch
- [ ] **Undo/redo for all edits** — currently only covers KKE changes; extend to tags, notes, nav assignments, group changes
- [ ] **CSV import for large files** — direct CSV support that bypasses SheetJS memory limits for very large crawls (10k+ rows)
- [ ] **Bulk notes + bulk tag remove/replace** — Multi-bar now supports bulk-appending one tag (`add-tag`), but there's still no bulk Notes editing, and tag editing is add-only (no bulk remove or replace)

## Methodology / Docs

### Unit-of-audit methodology (`docs/methodology/the-unit-of-audit.md`)

- [ ] **Verify the prior-art citations before adopting terminology or claiming novelty.** A research pass (Perplexity, 2026-08-28; source in the branch discussion) surfaced several practitioners who have documented pieces of this independently. Two terms are worth adopting *if they check out*, because they name things the page currently describes clunkily:
  - **"dark content"** — resources forgotten or unexposed even in the CMS admin, which neither a crawl nor a standard extract surfaces. Attributed to Marc Salvatierra / Content Aspects.
  - **"stranded nodes"** — content still published and search-indexed but quietly unlinked from navigation. Attributed to a Lullabot enterprise-inventory case study (Georgia state agencies).

  **Salvatierra is the citation to check first** — it carries the most weight in that research (the three-source merge, "dark content", and the Content Type / Presentation Type split all trace to it) and is the least independently corroborated. Lullabot, Jeff Eaton, Karen McGrane / Autogram "content observability", and Deane Barker's migration handbook are all plausible on their face but still unverified.
- [ ] **Read Paula Ladenburg Land, *Content Audits and Inventories* (2nd ed., 2023) before positioning this as new.** It is the field's standard reference and was expanded to cover automated tooling and content structure. The research pass dismissed it *from its published description without reading it* — which makes it the single likeliest place for this method to already exist, in whole or part. Build on it rather than around it.
- [ ] **Provenance-per-row instead of a two-store model** *(held — design note, not yet actionable)*. The research argued for separate `content_entity` / `crawl_instance` tables joined by a match table, so "what the database says exists" stays queryable independently of "what the crawl found". That requirement is legitimate; the two-table answer is not, since it forks every view in the app. The better answer is one row table plus a `_Source` field (extract / crawl / both) with match method and confidence — same queryability and audit trail, no fork. Fold into the technical proposal when it is rewritten.
