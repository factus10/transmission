Transmission

A desktop app for content audits, on macOS and Windows. It pairs a spreadsheet with an embedded browser so you can review every page on a website and record structured decisions without switching apps.

Many examples here come from higher education, but nothing in the app is specific to it: it works the same for any industry's site.

MRA is the core call on every existing page: Migrate · Archive · Revise · Consolidate · Exclude. The input is usually a Screaming Frog crawl export (.xlsx), but any spreadsheet with a URL column works. Every decision is written back into the same file — your deliverable is one enriched spreadsheet. Changes auto-save moments after your last edit (≈0.4s in a project, 2s in a spreadsheet; or Cmd+S).

This help follows the real lifecycle of an audit, top to bottom (Set up → Audit → Classify → Review → Architect → Ship → Power features). Each section opens with the one mental model that makes it obvious, the key steps, and a Good end-state checklist. For the full manual and task hand-outs, see the project's docs/ folder (docs/USER_GUIDE.md and docs/walkthroughs/).

A · Set up & orient

1. Getting Started

Mental model — one portable file is the whole project. Start from a crawl spreadsheet, then convert it to a .transmission project file (File → Save As Project…, Cmd+Shift+S) — same single-file promise, but saves are instant at any size. Excel becomes the import/export format: File → Export Full Workbook (.xlsx)… produces a complete spreadsheet (all sheets + change history) whenever you need a deliverable.

  • Open: Cmd+O (or the welcome dialog's Open a file). Formats: .transmission, .xlsx, .xls, .xlsm, .ods, .csv. File → Open Recent lists the 10 latest. Project files also open by double-click in Finder.
  • Hand-off: File → Package for Handoff… saves, snapshots, and zips the project (with a README) ready to send; the recipient unzips and double-clicks. Change-log entries record each auditor's username. A rolling safety copy is kept in the app's support folder on every open.
  • Client exports: File → Export… → Client Export exports a chosen column subset (built-in Client Summary / Full, or your own saved profiles — stored in the project) over filtered or all rows.
  • Sheet & URL: multi-sheet files show a picker (structural sheets hidden); the URL column auto-detects (Address, URL, …) or you pick it.
  • Seed banners: one-time offers of starter libraries (Content Type Registry, Target Spec Library, Component Library). Seeding stages data — save to commit.
  • Help: Help → Getting Started (welcome), Product Tour (5-step), Keyboard Shortcuts (Cmd+/ or ?), Online Documentation (the full manual, walkthroughs and method pages, opened in your browser), Check for Updates… (also checked automatically at launch — shows a What's New changelog and a download link; installing is still manual).

Good end-state

  • Right data sheet selected; URL column detected (rows load a page)
  • Audit columns + structural sheets present; seed banners handled deliberately
  • First Cmd+S succeeds and the file reopens with state intact

2. Project Setup

Mental model — two tiers. Project Settings travels with the file (client-specific: site domain, decision states, suggestion weights, statuses, assignees, saved filters). App Settings is per-user (auto-advance, visible clusters, API key, sidebar columns, column mapping).

  • Project Settings (File → Project Settings) — five tabs: Identity · Decision states · Suggestions · Migration · Saved Filters.
  • App Settings (⚙ button) — Appearance (System / Light / Dark) · Auto-advance · Show SME fields · Show Migration fields · Show Components cluster · Rubrics folder · Claude API key · Sidebar columns · Column mapping.
  • Turn on only the Show … toggles this engagement needs; blank metadata is hidden and every cluster collapses with a click.

Good end-state

  • Identity filled (at least Site domain — redirects/paths depend on it; one URL, the new site's, not a list of source sites)
  • Custom decision states / migration vocab defined if the engagement needs them
  • App Settings reflect how you work; Project Settings saved into the file
B · The core audit

3. Running the Audit Pass

Mental model — one row = one existing page. Selecting it loads the page in the browser and fills the field-bar clusters (Decide · Classify · Migrate · Components · CMS). You live in Decide; the loop is keyboard-driven.

  • Make the call: 1 Migrate · 2 Archive · 3 Revise · 4 Consolidate · 5 Exclude (0 clears). Auto-advance carries you on; ] jumps to the next unreviewed row.
  • Rationale & flags: Notes (dot when present); F flags/unflags (★); Assess runs the rubric.
  • Classify lightly: set Content Type (drives the crosswalk) — batch the rest later.
  • Browser: ← → ↻, viewport switcher (Auto / SM / MD / LG / XL), ◫ compare · 📷 screenshot · ⇊ extract content · 🔗 check links · ↗ open externally.

Good end-state

  • Every intended page has an MRA call (check with ])
  • Rationale captured where the call isn't obvious; tricky pages flagged (F)
  • Content Type set where it'll drive migration; saved

4. Finding the Work

Mental model — filters are stackable and AND-ed (text and MRA and group and field filters). The list always reflects the current filter, and the Multi-bar acts on exactly that set.

  • Search with a scope selector: All fields / URL / Title.
  • Site order (button in the Address header): pages placed in the sitemap in sitemap order, then unplaced pages grouped by site and URL path, with each section's landing page directly above its children, indented by level. Click the Address header for A–Z / Z–A.
  • MRA filter is a checkbox dropdown (multi-select, OR-ed) including special filters: Unreviewed, Flagged, Duplicates, SME conflicts/pending, Consolidate (no/dead target) — the no-target count also shows as a red ⚠ N Consolidate: no target chip beside the row count, click to filter — Shared sitemap node, Needs placement, Suggested disagrees / ≠ your call.
  • Field filters (+ Field filter) on any column: is blank / is not blank / contains / equals / starts with / ends with / is greater than / is less than. The two ordering operators compare numerically when both sides are numbers (handy for word count, status code, sessions) and fall back to ASCII order otherwise; blank cells match neither. Unclassified is a shortcut for Content Nature is blank.
  • Delete rows permanently (Multi-bar → ⚠ Delete rows permanently…) for crawl noise that was never a page. The only destructive action in the app: it can't be undone, it clears the session's undo history, and it asks you to type PERMANENTLY DELETE. It first reports what breaks — pages consolidating into a doomed row, sitemap placements, reviewed decisions, redirect destinations — and logs every removal. For a real URL you simply aren't auditing, use Exclude instead.
  • Save a combination (text + scope + MRA + group + field filters) and recall it; Cmd+F Global Search finds & navigates across all rows. In the Sitemap, Cmd+F searches the sitemap nodes instead (label, breadcrumb, number, path, notes, pattern, assignees) and the ◀/▶ buttons jump & scroll to each match, expanding collapsed branches as needed.

Good end-state

  • Scope matches what you're hunting; multi-check used for "either"
  • Field filters layered for precise slices (e.g. Sitemap_ID is blank)
  • Recurring slices saved as named filters

5. Bulk Operations

Mental model — the Multi-bar acts on a target set: your multi-selection if any, otherwise the filtered rows. The label says which ("Apply to N selected/filtered:").

  • Define the target: filter only, or multi-select (Cmd+click toggle, Shift+click range). Selection wins when both apply.
  • Apply an action: Set MRA · Set Published Status · Set Content Type · Set Content Theme · Set Group · Set Primary Tag · Add Tag → pick value → Apply. Archive-cleanup prompts fire for pages with a sitemap assignment/redirects.
  • Assign to Sitemap…: no value to pick — Apply opens a dialog to choose an existing node or create a new bucket (top-level or nested). Default-eligible pages are Migrate/Revise only (Final_MRA wins if set); check Include Archive / Exclude / unreviewed pages too to place everything — the routine case for a "current state" snapshot — with one extra confirmation if any of those are Consolidate pages. Choose Direct children (each page its own child node, slug/label auto-derived from URL/title) or Preserve URL structure (nests sections from each page's path, to a chosen depth). Already-placed pages are skipped. For fast initial placement of many pages at once — reorganize afterward with the Sitemap editor's drag-and-drop.
  • Create Sitemap from Audit… (Project menu): builds the whole starter tree from every eligible page's URL in one pass, no destination to pick — pick a bucket depth and Generate. The dialog predicts the tree first: how many top-level sections you'll get, how many hold a single page, and which crawl artifacts (/tag, /category, /wp-content) are in the mix. Worth reading — the tool can only find hierarchy your URLs already have, and on a flat CMS every article at /some-slug becomes its own top-level section (one real audit: 548 sections from 1,859 pages). Bucket depth won't change that, since sections come from the first URL segment. When it looks like that, the dialog offers to sweep the single-page sections into one named section as part of the same step, so what lands is a tree you can actually open. Merges into an existing sitemap by name rather than replacing it, so it's safe to re-run. It asks what the tree is for: picking where pages are today (a client-facing snapshot) offers Save a copy first… — build a snapshot in its own copy, because placing pages derives redirects, which is meaningless for a tree describing where pages already are.
  • Batch assess: Project → Run Rubric on filtered rows… scores the set into Suggested_MRA.
  • Rubrics travel with the project: Project → Rubrics… → Copy from my library stores a copy in the project file, so every auditor (and Claude) applies the same rules. A Consolidate rubric holds Patterns — Applies when · Unless · Judgment · Then · Cite · Ask instead — which Claude reads when it looks across the whole audit: Rubric sweep (the chat's + menu, or /rubric-sweep in Claude Code) finds the pages a pattern describes, reads them and their targets, and proposes what merges into what. Accepting a consolidation proposal sets the target exactly as the Consolidate picker does.

Good end-state

  • The bar's label confirms the right target before Apply; filter spot-checked
  • Archive-cleanup handled; batch-assess for scoring, hand-set MRA for judgment

6. Tagging, Grouping & the Glossary

Mental model — three fields, different jobs: Group (one per page, the bucket), Primary Tag (one, the headline descriptor), Tags (many, finer CSV). The Glossary keeps terms consistent with a per-name definition.

  • Apply in the Classify cluster (Group / Primary are single-select with + New…; Tags is a chip input). Bulk via the Multi-bar.
  • Project → Edit Glossary… — markdown Notes per tag/group (empty entries pruned on save; travels in MRA_Glossary).
  • Export for Word… writes a styled .html key of every term + definition.

Audience — who is this page for?

Mental model — the audience prioritization workshop's ranking, made load-bearing. A page can have decent traffic, pass every rubric rule, and still serve nobody the client invested in — that finding is unreachable without this.

  • Project → Audience Library… — each audience gets a tier (Primary / Secondary / Tertiary / Not a target) and a color. Seed starter list… offers a generic Higher education or General organization set to begin from; Paste from workshop… drops your own table straight in and is the better path whenever you have the client's own ranking. Travels on the Audiences sheet. Setting the tiers is the step that matters — everything downstream reads them.
  • Tag in the Audience cluster: Also serves (chips, grouped by tier) and Primarily for (auto-fills when only one is tagged). The cluster reveals itself once your library has entries.
  • Blank means unreviewed, not "serves nobody." Use the reserved — None (no target audience) entry for the positive call — only it argues Archive.
  • Tag in bulk. Multi-bar: Add / Remove Audience, Set Primary Audience. Worklists: the Needs audience and Serves no priority audience filters.
  • Audiences on the sitemap: the node editor's Audience section sets who a branch is for. Unset nodes inherit from their nearest ancestor. Node audiences fill untagged pages placed there, never overwriting and skipping Archive/Exclude: saving a node asks first, and assigning one page fills it right away. One Cmd+Z undoes either. Color the sitemap/treemap by Audience (sitemap).
  • Project → Fill Audiences from Section… — spreads audiences you already tagged in a section onto that section's untagged pages. Free, no API key, fills blanks only, one Cmd+Z. A section needs 3+ tagged pages with an audience on half of them before it can speak for the rest. — None is never inherited.
  • Project → Suggest Audiences with AI… (needs a Claude API key in App Settings) — reads title / H1 / meta / URL / section against your library and proposes who each page serves. It never writes the Audiences column: suggestions go to a review queue grouped by answer, so thousands of pages become a few dozen decisions. Or take them one at a time from the ghost in the audit bar. Audience suggested by AI is that worklist.
  • Feeds Suggested_MRA as a weighted source, colors the Visual Sitemap and Treemap by Primary Audience, and rides along in the Migration Tracker and SME export.

Jobs to be done

Mental model — audiences answer who; jobs answer what they came to do. The payoff is the inverse: a job with no page serving it is the strongest brief for net-new content, because it traces back to the client's own workshop.

  • Project Settings → Audience → Jobs to be done — short label (what you tag with), full statement, and which audiences have it (blank = anyone). Paste from workshop… takes the table.
  • A Jobs served field appears in the Audience cluster once the library has entries. The picker hoists jobs belonging to this page's audiences to the top.
  • Bulk-tag with Add Job; Needs a job is the worklist filter.
  • Reports → Jobs Coverage leads with jobs nothing answers; the same list is appended to the Net New Content Brief.

Good end-state

  • Every page has a Group; Primary Tag where one descriptor dominates
  • Tags drawn from a deliberate reused set; every active term defined
  • Audience library reflects the workshop, with real tiers set
  • Every Migrate/Revise page is tagged, or on the Needs-audience worklist
  • No AI suggestions left unreviewed (the Audience suggested by AI filter is empty)
C · Classify for migration

7. Content Types & the Crosswalk

Mental model — three linked attributes: Content Type (what it is — the key), Renders as (Page / Record (own page) / Fragment (embeddable, no URL) / Generated — a news post migrated as a record is a Record, not a Fragment: it still needs a redirect), Target Content Type (what it becomes). The Content Type Registry is the crosswalk — define once per type, every page inherits it, non-destructively.

  • Set Content Type as you audit (a → hint shows the mapped target). This is the one classification worth doing on the main pass.
  • Project → Content Type Registry… — per type: Renders as · Target Content Type · → Target Spec · Migration Track · Notes. Seed with defaults stages ~20. The editor also lists content types in use without a crosswalk (flagged “in use · no crosswalk”) so gaps are fillable; a Show all pick-list types toggle adds unused global dropdown values. Untouched surfaced rows aren't saved — only mapped ones persist.
  • Adding a type via the audit bar's + New content type… seeds a blank registry row automatically (skipping anything already covered) — the global dropdown and the per-project crosswalk stay in sync.
  • Defaults fill blank Renders as / Track / Target only (never overwrite). The Migrate cluster's Track shows a ghost suggestion when blank.
  • Verify: the Unclassified button finds missing Renders-as; Reports → Content Type Crosswalk… flags types with no entry.

Good end-state

  • Every migrate/revise page has a Content Type; registry covers every type in use
  • Renders as populated (Unclassified → 0); Target + Target Spec + Track mapped

8. Suggested_MRA

Mental model — a thin orchestrator over up to three sources — Rubric (rules), AI (Claude), GA (analytics composite). It combines them by weighted vote into one suggestion and never touches your human MRA.

  • Set up in Project Settings → Suggestions (GA mapping/weights, rubric folder, source weights).
  • Generate: Run Rubric on filtered rows… · AI Suggest for Unreviewed… (blank-MRA rows only, ~1s/row, Esc aborts) · Refresh GA MRA. Recompute Suggested MRA re-runs the combine.
  • Read: the Suggested_MRA badge (source prefix, ⚠ on disagreement; click for the breakdown). Sidebar filters Suggested disagrees / Suggested ≠ your call focus your judgment.

Good end-state

  • At least one source configured; weights reflect trust
  • Disagreements/mismatches reviewed; human MRA confirmed where it counts

9. Consolidate

Mental model — Consolidate merges a page's content into another (recorded in Consolidate_Into); the target survives (usually Revise). Consolidated pages need no sitemap placement; the redirect resolver chases the target (cycle-safe). The app warns on a dead target.

  • One page: press 4 / click Consolidate → pick the target in the picker (sets Consolidate_Into + MRA, clears sitemap placement).
  • Final MRA wins: whether a page consolidates follows the client's Final MRA, not the recommendation. When they differ, a Final chip appears beside the MRA buttons (click it to pick a target or open the Final dropdown). SME → Review Consolidations… lists every consolidation the client changed, plus agreed ones where the SME left notes, so you can choose, confirm, or clear each target.
  • In bulk: Sitemap → Consolidation Candidates… lists nodes with 2+ pages; pick the target (→ Revise), the rest become Consolidate.
  • Automatic catch: marking a page Migrate/Revise (or assigning its sitemap node) when another Migrate/Revise page already sits at that destination pops a "Did you mean to Consolidate?" prompt with a one-click target.
  • Jump to the target: reopen the picker (click Consolidate again) and use Go to page → next to the current target.
  • Catch breaks: sidebar filters Consolidate (no target) and Consolidate → Archive/Exclude target; the no-target count also appears as a chip in the sidebar toolbar whenever it isn't zero.
  • Guardrails: a page can't consolidate into itself, or into a page that consolidates back into it (a redirect loop plus content that never lands). Picking a target marked Migrate, Archive, Exclude or unreviewed prompts to set it to Revise — receiving content is work, and Revise is the signal — overridable, and it updates Final_MRA too when one is set.

Good end-state

  • Every Consolidate page has a live target (no "no target" / "dead target")
  • Targets survive as Migrate/Revise; redirects resolve to a real URL

URL Variant Triage

Mental model — a crawl lists URLs that responded, not pages. Pagination, sorting, facets and tracking parameters produce many URLs for one page. The site says which via rel=canonical; Transmission reads that rather than guessing from parameter names.

  • Project → Triage URL Variants… — groups variants by the page they point at, largest first.
  • Query only (same path) → Exclude; the canonical's redirect already covers them. Different path → Consolidate into the canonical, which writes the redirect.
  • Nothing is hidden — every page keeps its row and gets a logged decision, and Cmd+Z reverses the whole triage in one step. Out-of-scope sites are skipped.
  • Filters: Alternate view of another page (canonical) · Canonical target not in this crawl.

10. Non-200 Triage

Mental model — a crawl is full of non-200 URLs (3xx/4xx/5xx) — mostly cleanup, not content decisions. Triage groups them by status code and sets a default MRA per group at once.

  • Project → Triage Non-200 Pages… (or the auto-offer on open) — one row per code with a pre-set MRA dropdown; adjust, leave blank to skip, Apply.
  • Sidebar status-code badges (amber 3xx, red 4xx/5xx) help you spot what's left. Triage never hides rows — a 404 might be a live page behind a wall.

Good end-state

  • Each code group given a deliberate action (or intentionally skipped) and applied
  • No unexpected red/amber rows left unreviewed
D · Collaborate & review

11. SME Review

Mental model — export → reviewer fills dropdowns → import → resolve. The SME needs only Excel; their columns (SME_Decision, SME_Notes, Content_Owner) merge alongside your audit — never overwriting your MRA.

  • SME → Export for SME Review… (optionally split by Content Owner); embedded dropdowns constrain choices. For a client whose project began before the rename, tick Use Keep / Kill / Evolve wording to send that worksheet in the old words.
  • SME → Import SME Decisions… merges by URL. A worksheet in Keep / Kill / Evolve is read as Migrate / Revise / Archive (Change: Kill → Archive), and the import says how many decisions it re-worded. Compare MRA vs SME… shows divergence; Resolve Conflicts… sets Final_MRA.
  • Reconcile inline with Show SME fields; sidebar filters SME conflicts / SME pending.

Good end-state

  • Imported; Compare reviewed; Resolve run (every reviewed page has a Final MRA)
  • SME conflicts / pending filters empty

12. Multi-auditor Merge

Mental model — merging reads the other auditor's file, matches rows by URL, and reports agreements vs conflicts (different MRA on the same page). You resolve conflicts — never silently overwritten.

  • File → Merge Auditor Decisions… → pick the other file. Empty cells fill automatically; conflicts open a resolution dialog (per-row, or bulk Accept All Theirs / Keep All Mine).
  • Related: File → Import/Merge fills only blank cells and can add new URLs.

Good end-state

  • Other file merged; every conflict resolved (0 remaining); saved as canonical
E · Architect the future site

13. Sitemap & IA

Mental model — the sitemap is how your content is organized (sections, hierarchy, where each page lives); the Visual Sitemap turns it into a shareable box-tree so people can see that organization. Audit rows answer "what about each existing page?"; you connect them by placing Migrate/Revise pages onto nodes. The URL path and on-page breadcrumb are derived from the sitemap by default (renames cascade) but are not bound to it — organize freely, then use the per-node URL override / breadcrumb override where the real site should diverge (e.g. a department organized at Home › Academics › Departments › Chemistry can publish at /chemistry with breadcrumb Home > Departments > Chemistry).

  • Open with Cmd+Shift+T (or the Sitemap tab). Drive need placement → 0: MRA = Migrate + Revise, field filter Sitemap_ID is blank, then the audit bar's Sitemap button → Assign (use + Child to create a node inline), or the Multi-bar's Assign to Sitemap… for many at once. Starting empty? Project → Create Sitemap from Audit… builds the whole starter tree from the crawl's URLs in one pass (pick a bucket depth); or, with no nodes yet, the audit bar's Sitemap button offers an inline form for just the current page.
  • Shape: rename/re-slug inline (cascades), drag to reorder/reparent, + Root Node / row +, ⧉ clone, Remediate. Set Node type, Collapse (bulk Collapse ✓ / Expand — summarizes a subtree in the Visual Sitemap), Reference, Phase.
  • Preview: the toolbar's Preview button opens the assigned web page beside the tree. While it's open, click a row to show that node's page (‹ 1 / 3 › steps through a node with several); click a page in a node's expanded page list to preview it, or its Audit → button to open it in the Audit view. Header buttons: reload, open in your browser, Open in Audit. Drag the pane's left edge to resize; open state and width are remembered.
  • Gaps: NEW = net-new (double-click → amber banner → set Page Status or click Create Page to promote it into a real Migrate row assigned to the node); red empty leaf = assign / net-new / phase / delete; ⚠ duplicate IDs auto-renumbers. Read the stats line.
  • Bulk select & delete: each row has a checkbox (click, Shift+click for a range — collapsed/hidden rows are never swept in, header checkbox = select all visible). Select Empty Branches checks every branch with zero assigned pages anywhere underneath in one click. Delete Selected… deletes the full subtree of each pick (a selected descendant of an also-selected ancestor is skipped — the ancestor already takes it) after one confirmation; Cmd+Z undoes the whole batch in one step, same as a single-node delete.
  • Decouple the three axes (all in the node editor): URL override (↪) publishes a page at an address off its menu position, re-rooting sub-pages; Breadcrumb parent (↰) sets an arbitrary on-page breadcrumb top (e.g. deep Accounting reads Home > Accounting) — optional Home prefix + advisory depth cap in Project Settings → Identity, and a Page Breadcrumb column in the Migration Tracker / sitemap & menu exports; and Menus (below) are independent of the tree. Containment, URL, breadcrumb, and menus are four separate things.
  • Shape check: a sitemap can be valid and still be too big to draw. When yours is, the app says so before opening the diagram (and the toolbar stats line carries a clickable ⚠). It reports the section count, the exact diagram size and the zoom it would open at, then names the causes with a repair for each: top-level sections holding a single page (the flat-site signature — move them under one section), crawl artifacts like /tag and /wp-content (remove the sections; pages stay in the audit, unplaced), and sections too wide to lay out (mark collapsed). Ticking repairs shows the tree you'd end up with — and will tell you plainly when they aren't enough, because grouping hundreds of pages into the handful of real sections the new site needs is judgement, not a button. It also answers "shouldn't there be a site-root box?" by measuring it. Open the diagram anyway is always offered: "this site has no IA" is a finding worth showing a client.
  • Visual Sitemap (toolbar Visual Sitemap): the content IA as one interactive box tree rooted at the homepage. Click a card's +/− to collapse/expand it (only the +/− toggles — the card body is inert), scroll to zoom, drag to pan, Fit (Shift+1) or 100% (Shift+0). The zoom readout sits between − and +, and clicking it also jumps to 100%. Expand all / Collapse all re-fit the view. The Counts dropdown sets the small line under each label: Hidden sub-pages (default — a collapsed card reports how many pages are folded underneath it, e.g. 6 pages hidden), Sub-pages on every branch, Assigned audit pages (the original per-node tally), or None. Saved with the project; honored by the HTML / PDF / Miro exports. Branches auto-lay-out horizontal vs vertical by two thresholds (Vertical from depth, or if children ≥); right-click a node to force a direction or set its color. Hide in diagram (node editor → Identity) leaves a node and everything under it out of the Visual Sitemap and its exports. Use it for pages that need mapping but not drawing, such as user profiles, while the node keeps its pages, URL, redirects and report rows. Large branches (Settings → Layout): a branch with more than 25 direct children opens collapsed, with its card saying how many pages it hides. Expanding one lasts until you close the diagram and doesn't change the Sitemap editor's Collapse checkbox. A top-level node with more than 30 children stacks them in a column instead of one very wide row. Set either number to 0 to turn it off. Settings panel: Layout (Parent position — centered over children, or left-aligned so the root anchors the top-left and the tree grows right; sizes/gaps, plus Corner radius and inner Padding L/R / Padding top/btm — global looks, not per-rule, and capped so they can't squeeze a label out of its card; and a Connectors section — Line color for every connector, and Line weight set to Uniform or By content volume, where each line's thickness reflects how many pages sit beneath it: a 200-page section draws as a thick trunk, a 4-page corner draws thin. Base width / Max width are the two ends of that scale, which is compressed so one huge section doesn't flatten the rest into identical hairlines. Carries into the HTML, PDF, PNG and Miro exports), Colors (next bullet), Legend (editable labels), and Save as my defaults. Long page names clip at the card edge with the full name on hover. Export an interactive HTML file for the client (collapse/zoom in any browser), a one-page PDF, a plain PNG image (the whole diagram at its natural size — for slides and docs that won't place a PDF), or Export to Miro (see 16). Also Sitemap Coverage & Net New Content Brief (the navigation hand-off report is now the Menu Report, in the Menus view).
  • Colour rules (Visual Sitemap → Settings → Colors): pick a Card style — Colour band (colour on a strip across the card top) or Heavy outline (white card, thick coloured border — the convention most sitemap decks use, and clearer at scale); switching converts existing rules and keeps their colours. Rules can test 15 dimensions: from the node (Phase · Node Type · Page Status · Build Pattern · Builder · Writer · Migrator) and from the spreadsheet (Content Type · MRA · Final MRA · Renders as · Migration Track · Content Theme · Published Status · Target Content Type), plus Depth / Top-level section / Links to another site. Spreadsheet dimensions appear only if that column exists, and the Colour by this picker shows coverage (38/121, or no data — greyed out) so you can see which are worth using. A node holds several pages, so normal operators (is, is not, …) test its dominant value while any page is asks whether any page underneath matches — that's how you flag a section merely containing something (e.g. one Archive inside a Migrate branch). A rule can carry several conditions (all must match); one with none is the catch-all and goes last. Generators: By depth · By section · Mark external · Colour by this. Right-click a card → Set color beats every rule.
  • Rules compose — each property (colour, fill, line style) is claimed by the first matching rule that actually sets it, so two dimensions can be encoded without a rule per combination. Put the rules that own the colour above the ones that own the line style (solid / dashed / dotted, or leave unset): e.g. four Builder rules for colour, then three Page Status rules for line style — seven rules instead of twelve. Order matters; flip them and the status rules claim the colour too. Drag to reorder. Phased nodes stay dashed whatever a rule sets, so a dashed card always means "not in this build".
  • Treemap (toolbar Treemap, next to Visual Sitemap): the same content as space-filling boxes sized by page count — how much of the site is what, at a glance. A small dialog picks Depth (how many levels before deeper nodes roll up into the box above them — 1 / 2 / 3 / Unlimited) and Color by (MRA decision or top-level section at any depth; Phase / Node Type / Page Status / Build Pattern / assignee only at Unlimited depth, since a rolled-up box has no single value to report), then Generate — reopen the dialog to change either, since both re-roll the aggregation. Which colours are used is yours to set inside the view: open the Legend and each entry has a colour well (recolours every box in that category); right-click any box to override just that one, for calling out a single section in a client deck; Reset colors puts it back. Saved with the project, kept per colouring mode, and carried into every export. Only leaf boxes are recolourable — a box with visible children is structural chrome, not a category. Pan/zoom/Fit, a legend, and the same Export HTML / Export PDF / Export PNG / Export to Miro as the Visual Sitemap.
  • Content Flow (toolbar Content Flow, next to Treemap): the migration itself as a flow diagram — current-site sections on the left, new-sitemap sections on the right, every band's thickness a page count. Three readings toggled inside the view: → Decision (the current site mapped straight onto its Migrate/Revise/Archive/Consolidate/Exclude calls — plus any states you've added yourself, each with its own block and colour, and an (unreviewed) block for pages nobody has looked at yet), → New sitemap (“where did this section's content go”), and → Decision → New, which shows both at once — usually the version to show a client, since it makes the decisions the visible pivot. Colour bands by decision or by source; hover any band or block to isolate its flow. The three non-section endpoints are the honest part: Retired (Archive), Out of scope (Exclude), Not yet placed — often the biggest block on the diagram. Consolidated pages flow through to their master's destination (the URL dies, the content survives), chained consolidations included. Current-site sections are read from the URL path — not from where a page is placed, or every placed page would flow to itself — with shared path prefixes and locale prefixes stripped per host. A small dialog picks the depth of that axis (top-level, or 2–3 segments) and which reading to open with. Pan/zoom/Fit, a legend, and the same Export HTML / Export PDF / Export PNG / Export to Miro. Every export renders the view you're looking at — toggles and colouring included — and the exported HTML opens on it with the other readings still available. On a Miro board the flow becomes blocks and weighted connectors (Miro has no ribbon shape): the reading survives, but band thickness is Miro's 1–24 stroke scale rather than the exact proportion, and blocks get a minimum height so labels fit.
  • Content Flow on a multi-site consolidation: a left column of current-site sections gets unwieldy fast — five sites × a dozen sections is sixty blocks, more than the diagram can draw legibly. So when the audit covers more than one source site, a Source site / Current section selector appears and Source site leads by default: which site contributes what, and where it lands — four or five blocks instead of sixty, with the merge showing as several sites' bands converging on one new section. Source sites start out named after their domain — all the app can infer — so the setup dialog offers a rename box for any that still are, since that name labels a whole column of a client-facing diagram. Editable any time in Project Settings → Sites (also where you assign hosts to sites, record CMS/owner, and set scope); renaming updates every page's Source Site. On a single-site audit nothing is asked — the diagram is titled from Project Settings → Identity. Sites marked out of scope are excluded (a note says how many rows), section names are qualified by site (Beta College › About) so two sites' /about can't merge, and a site served from both www. and a subdomain still counts as one. Crowded columns group everything past the top 20 into one Other block — totals still add up, and a note says how many were folded.

Menus

Mental model — the tree says where content lives; menus say how people reach it — not the same thing. Menus are independent structures that reference content pages, so the same page can appear in several menus at different depths, and a menu's shape need not match the hierarchy.

  • Open the Menus tab (or Cmd+Shift+M). Left = your menus (drag to reorder); right = the selected menu. + New Menu, or Seed from content tree to mirror the in-menu sitemap nodes as a starting point, then edit independently.
  • Add a page from the audit view: the audit bar's Menu button adds the current page to a menu without leaving the audit. Since menus reference pages on the sitemap, it first makes sure the page is on the sitemap (prompting you to add it if not), then opens a chooser of your existing menus (plus + New menu…); with no menus yet, it opens a New menu dialog (Name / Placement / Description) and adds the page to it.
  • Items, three kinds: + Page (references a content page — live label/path, flags broken refs), + Link (external URL), + Header (label-only grouping). These toolbar buttons add at the root; switch a kind anytime via the page / link / header dropdown on the item. This toolbar row stays pinned at the top while you scroll a long menu.
  • Drag the ⠿⠿ grip to reorder or nest (top/bottom third = before/after, middle = nest). Flat or as deep as you like, per menu. Each item also has a + (add a Page/Link/Header as its child directly, no drag needed) and ⧉ (duplicate the item and its whole subtree as a sibling).
  • Per-menu context: a Placement (per-project vocab — Top bar, Footer, Overlay / Fly-out… add your own) and a free-text Description. Menus travel with the file.
  • Duplicate menu clones the whole menu — name, placement, description, item tree — so you can test an alternate structure without touching the original. The copy is auto-selected, and Export…'s "just this menu" scope defaults to it.
  • Export… (CMS-agnostic): a neutral structure any platform maps from — choose all menus or the selected one, as a flat Excel Menus sheet or nested JSON. Page refs resolve to target URLs; no vendor model baked in.
  • Broken refs: if a page a menu references is deleted, the item shows (missing page) and a red ⚠ broken refs button appears — click to re-pick or remove each. Check before handoff.
  • Report: a tight hand-off doc (PDF / HTML) — one card per menu with its item tree, page-count badges on refs, ↗ links, ≡ headers, red missing on broken refs.
  • Sitemap: draws your menus with the same interactive engine as the Visual Sitemap (above) — each menu a tree stacked under its name, items colored by kind, headers dashed. Collapse/expand, smart horizontal/vertical layout with right-click overrides, the Settings panel (Layout / Colors / Legend), zoom/pan, and Export HTML (interactive) / Export PDF.

Good end-state

  • need placement = 0; no unexplained empty leaves; no duplicate Sitemap_ID/slug warnings
  • Phased work marked; net-new intentional; big repeating branches collapsed in the sitemap

14. Build & Direction

Mental model — every build node carries direction for three roles — Builder, Writer, Migrator. Direction lives at two levels: type-level defaults on the Target Spec, node-level briefs that override. Write the brief once per spec; the rest follow.

  • Project → Target Spec Library… — each spec is a Page Template or Content Model (field schema) with three direction defaults: Writer brief · Build guidance · Migration mapping. Matched by exact name; 12 seedable defaults.
  • Annotate nodes in the editor's Build / Write / Migrate sections (Pattern, Page status, Builder, Build guidance, Writer, Writer brief, Migrator). Applying a Pattern fills blank briefs (a Keep/Append/Replace diff dialog guards populated ones).
  • Vocab: Project Settings → Migration (Page Statuses + the shared Builder/Writer/Migrator Assignees pool). Fragments are typed via Node type.
  • Worklists: Reports → Migration Direction Brief… — Role (Writer / Builder / Migrator) + Person, grouped by spec. Each node lists the source page(s) assigned to it, and any page absorbing others shows a merges N flag (the old pages being consolidated into it).

Good end-state

  • Every build node has a Pattern (each with a default brief, or one reference page)
  • Builder/Writer/Migrator assigned; status reflects reality; specs carry a migration mapping

15. Redirects

Mental model — a redirect is needed for any Archive page and any page whose URL is changing. The app resolves destinations by priority (custom → sitemap node path → project default → blank). The literal 404 means "let it die" (distinct from blank = TBD).

  • Open with the Redirects tab / Cmd+Shift+R (lists Archive + URL-changed pages; fragments excluded).
  • Audit-bar badge: when the selected page has a redirect, an amber ↪ /path badge shows in the Decide cluster (full URL on hover) — click it to open that page in the editor, or the × to clear the destination. An intentional 404 shows as a 404 badge.
  • Set efficiently: Re-derive from sitemap (placed rows, plus unplaced Archive/Consolidate rows whose destination the app derived), the per-row sitemap picker, the 404 toggle, and Find/Replace (filters to matches; Replace All). Destinations also resolve on Save.
  • Redirects vs the sitemap: Migration → Redirect Health Check… finds destinations that no longer match where the sitemap sends the page — loops (a page redirecting to itself), Migrate/Revise pages carrying a redirect while not on the sitemap at all (they aren't moving), and destinations pointing at a tree that has since been rebuilt. Common after a “current state” sitemap is built and deleted. Tick the groups to repair; the whole fix is one Cmd+Z. Anything that still resolves to a real node is reported but never changed.
  • Validate & export: Migration → Redirect Chain Check…; Export Redirect Map (CSV)…; Reports → Redirect Map Report… (built from the same rules as the CSV: pages that still need a destination, removed, consolidated, URL-changed, intentional 404s).

Good end-state

  • Every Archive/URL-changed page has a destination (or an intentional 404)
  • Re-derived after the tree was finalized; chain check clean; map exported

16. Producing the Outputs

Mental model — reports are read-only views generated on demand; each exports to PDF or HTML (HTML opens cleanly in Word). Three audiences: stakeholder narratives, IA/structure, delivery/engineering.

  • Stakeholder: Executive Summary · Content Inventory by Section · SME Review Status.
  • Redirect Chain Check (Migration menu) covers inherited 3xx redirects. Their destinations are re-derived every save, so a rule follows its target if that page moves, is consolidated or is retired — and a live-site chain collapses to one hop. The report groups what can't be resolved automatically: no destination recorded · redirects to itself · destination is a dead 4xx · destination has no MRA decision yet · destination is being retired with nowhere to go · destination not in this crawl · destination on an out-of-scope site. The undecided check keys on the MRA decision rather than sitemap placement, so it works the same on a migration that preserves every URL and never builds a tree. Off-site destinations carry forward verbatim. Filter: Inherited redirect needs review.
  • The Executive Summary counts content pages, not crawled URLs — inherited redirects (3xx) and dead URLs (4xx) are broken out separately and excluded from every figure below, including the Archive percentage, so nobody reads "pages to migrate" off a number that is mostly redirects. A 5xx still counts as content (a broken page is a page). Sidebar filters Existing redirect (3xx — not content) and Not content (3xx or 4xx) show the rows behind it.
  • IA & structure: Menu Report · Sitemap Coverage Report · Content Type Crosswalk · Component Inventory · Audience × Section Matrix (sections down, audiences across, cells shaded by share — surfaces "this whole section is written for the wrong people").
  • Consolidation: Site Consolidation Overview (what each source site contributes — pages, disposition, audiences, overlap, redirect rules) · Cross-Site Duplicate Overlap (same title+H1+meta on 2+ sites — the merge worklist).
  • Jobs: Jobs Coverage (per job: pages serving it, best page, and the jobs nothing answers — the net-new brief).
  • Audience: Audience Coverage (pages per audience in tier order, with MRA mix and an under-served-Primary flag; its Risks section covers off-strategy content, pages serving nobody, priority pages marked Archive, and detail pages serving 4+ audiences. Landing pages serving many audiences are expected and not counted).
  • Findings & appendix: most reports open with Key findings and Next steps. Working lists sit in a For the audit team appendix, left out of exports unless you tick Include audit-team appendix in export.
  • Delivery: Migration Direction Brief · Migration Checklist (one page: readiness, decisions, redirect totals, pages to write) · Build Status (Page Status by section and by person, blocked pages) · Net New Content Brief (writer hand-off: landing pages, new pages, placeholders, grouped by writer) · Redirect Map Report.
  • The Migration menu holds export/validation tools; the Progress Dashboard (Cmd+P) gives live completion stats.
  • Ask the audit a question (MCP server, developer preview) — for the questions no report answers (how many Migrate pages under /news have no audience?), a small MCP server in the Transmission source (mcp/server.js) lets Claude Desktop, Claude Code or any MCP client read a .transmission project: counts grouped by any column with filters, page lists, one page's full record and history, the sitemap with page counts, redirects with provenance, the audit trail, the libraries, and your saved filters by name. It sends the model the conventions that matter (blank = unreviewed, Archive vs Exclude, content pages vs crawled URLs). It is read-only — it never changes the file, and is safe to use while the app is open (it picks up each autosave). A session started any other way connects to whatever Transmission has open. Spreadsheets aren't supported — Save As Project first. It hands project data to whichever model the client is connected to, so check the engagement's data terms first.

Rubric DSL

Rubrics are markdown files (one per status) in a configurable folder; each has ## Field Rules (auto-evaluated — the status with the most passing rules wins) and ## Content Rules (plain-English checklist for manual / AI review).

# Migrate

## Field Rules
- Status Code is 200
- Indexability Status is Indexable
- Word Count > 500

## Content Rules
- Page provides comprehensive coverage of its topic
- Content is current and regularly maintained

Transmission stores every column in your crawl losslessly — including any custom extraction columns you set up in Screaming Frog (XPath/CSS/regex pulls: CMS IDs, author bylines, publish dates, schema markup, component flags, etc.). Nothing is dropped or renamed when you open the file or convert it to a .transmission project, and everything round-trips back out intact on Export Full Workbook. Those columns aren't just preserved — they're usable: surface any of them in Table View, pin them to the field bar (Preferences → Sidebar columns / field picker), or filter on them with + Field filter (e.g. CMS Template is not blank). The app treats your columns and the audit columns the same way.

Tips & Best Practices

Speed up your audit

  • Use 1–5 for MRA and enable auto-advance to fly through pages; ] jumps to the next unreviewed.
  • Set up rubrics early — even a few field rules per status catch the obvious pages.
  • Use Batch Assess / AI Suggest for Unreviewed to seed Suggested_MRA, then confirm.

Stay organized

  • Assign Groups early; use Primary Tag for the dominant characteristic.
  • Flag pages to revisit with F; save named filter combos for views you return to.

Work with your team

  • Use audit templates for consistent setup; export SME subsets by Group or Owner.
  • Merge parallel auditors' files; the changelog tracks every decision change.

Sitemap, redirects & hand-off

  • Place every Migrate/Revise page (need placement → 0) before deriving redirects.
  • Re-derive redirects from the sitemap after restructuring; run the chain check before export.
  • Run the Pre-Handoff Check last — fix what it flags, then export the Migration Tracker.
